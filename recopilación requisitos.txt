OBJETIVO FUNCIONAL
1) El usuario puede programar un aviso (reminder) para una entry (task/note) a una fecha/hora.
2) La API debe encolar un job con delay en BullMQ.
3) Un worker ejecuta el job cuando toca y hace una llamada HTTP a n8n.
4) Debe existir notificación en dashboard cuando el reminder se envía o falla.

DOMINIO
Reminder:
- id
- userId
- entryId
- scheduledAt (ISO datetime, UTC recomendado)
- channel (string: "whatsapp" | "email" | "push" | etc, por ahora libre)
- status: "pending" | "sent" | "canceled" | "failed"
- createdAt, updatedAt

Notification:
- id
- userId
- type: "REMINDER_SENT" | "REMINDER_FAILED" | "REMINDER_CANCELED"
- title
- message
- status: "unread" | "read"
- payload json (opcional)
- createdAt

VALUE OBJECTS
- ISODateTime (valida formato ISO; almacenar en DB como timestamptz)
- ReminderStatus
- Channel (string no vacía)

VALIDACIONES
- scheduledAt debe ser futuro (tolerancia 1-2s). Si no, 400.
- Ownership: 404 si entry/reminder no existe o no pertenece al user.
- Cancelar: solo si status == pending (si ya sent, 409).

API ENDPOINTS
A) POST /api/reminders
Body:
{
  "entryId": "string",
  "scheduledAt": "2026-02-04T18:30:00.000Z",
  "channel": "whatsapp",
  "message": "opcional"
}
Responses:
- 201 { reminderDTO }
- 400 invalid
- 401 no auth
- 404 entry no existe / no es del user

B) PATCH /api/reminders/:id
Body:
{
  "scheduledAt"?: "ISO datetime",
  "channel"?: "string",
  "status"?: "canceled"
}
Rules:
- Permitir reprogramar solo si pending.
- Permitir cancelar con status:"canceled" solo si pending.
Responses:
- 200 { reminderDTO }
- 400, 401, 404
- 409 si no se puede (p.ej. ya enviado)

C) GET /api/notifications
Query optional: ?since=ISO datetime
- 200 [{ notificationDTO }]
- 401

D) POST /api/notifications/:id/read
- 200
- 401, 404 (ownership)

WORKER (BullMQ)
- Crear cola "reminders".
- Al crear reminder: encolar job con jobId = reminderId y delay = scheduledAt - now.
- Worker consume:
  1) carga reminder por id desde Postgres
  2) si status != pending -> no hace nada (ack)
  3) llama a n8n webhook por HTTP POST con payload:
     { reminderId, userId, entryId, scheduledAt, channel, message }
     - Firma HMAC (X-Signature) con secret N8N_WEBHOOK_SECRET + timestamp (X-Timestamp) para evitar spoofing
  4) si n8n responde 2xx -> marcar reminder sent + crear notification REMINDER_SENT
  5) si falla -> marcar reminder failed + crear notification REMINDER_FAILED
- Con reintentos:
  - attempts: 5
  - backoff exponencial (p.ej. 1m, 5m, 15m...)
- Concurrency configurable (por env, default 5).

IMPORTANTE SOBRE “CANCEL / RESCHEDULE”
- Para MVP, no es obligatorio borrar jobs antiguos del queue.
- Implementa la estrategia simple y robusta:
  - los jobs pueden quedar “huérfanos”
  - el worker siempre revalida en DB: si status no pending o scheduledAt cambió, entonces no envía.
- Deja TODO si quieres optimizar removiendo jobs por jobId.
